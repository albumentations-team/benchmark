\begin{abstract}
We measure eight input paths from RGB JPEGs on disk to a synchronized CUDA
\texttt{float16} batch. All measurements use the same Google Cloud
\texttt{g2-standard-16} configuration with an NVIDIA L4. The report contains
\ProductionCellCount{} measurements across \RecipeCount{} recipes, with throughput and peak
process GPU memory recorded together. On the \CommonRecipeCount{} recipes shared
by all eight paths, DALI averaged \CommonMeanDaliRatio\(\times\) the throughput
of AlbumentationsX (AX) 2.6.2. Median peak process memory was
\CommonMemoryDALIGPU{} MiB for DALI and \CommonMemoryAlbumentationsX{} MiB
for AX. Across \AllSIMDShared{} shared
recipes, Pillow-AllSIMD in fast mode had a median throughput ratio of
\AllSIMDMedianRatio\(\times\) versus Pillow. Its MedianBlur recipe reached
\AllSIMDMedianBlurRatio\(\times\). A separate census maps
\CoverageAlbumentationsX{} selected AX RGB entries to corresponding APIs.
Benchmark code: \url{https://github.com/albumentations-team/benchmark}.
\end{abstract}

\section{Introduction}

A model consumes batches, so a faster transform can have little effect if
JPEG decoding, collation, or transfer takes most of the time. A GPU input
pipeline also competes with the model for device memory. We measure how many
ready images each path delivers per second and how much GPU memory its
process occupies. We also count the correspondences recorded for a selected
AlbumentationsX transformation catalog.

\paragraph{Relation to other measurements.}
Operation timing tools, such as PyTorch Benchmark, measure selected code blocks
with warm-up and synchronization controls~\cite{pytorchbenchmark}. Mohan et al.
analyze fetching and preprocessing stalls within DNN training~\cite{datastalls}.
MLPerf evaluates training systems using time to a specified quality target,
which accounts for effects beyond raw training throughput~\cite{mlperf}.
Our experiment measures throughput and process memory for the input pipeline
alone. Model execution and contention between the model and loader are outside
the measurement.

\section{Workload and measurement}
\label{sec:workload}

The image operations vary by recipe. For example:
\begin{quote}
\textbf{R02}\quad\texttt{RandomCrop224}\\[3pt]
\textbf{R22}\quad\texttt{RandomCrop224 $\to$ Equalize}
\end{quote}
Every path applies channel-wise mean and standard deviation normalization
on the GPU after augmentation. The DataLoader paths transfer a collated
tensor to CUDA before normalization. DALI normalizes inside its GPU graph.
The formula uses RGB means
\((0.485,0.456,0.406)\) and standard deviations \((0.229,0.224,0.225)\)
on the unit intensity scale. All paths deliver a contiguous CUDA
\texttt{float16} batch in BCHW layout with shape \(256\times3\times224\times224\).
The catalog label \texttt{ToTensor} specifies this output contract.

R02 and R22 both time the full input path from JPEG to ready batch.
Appendix~\ref{app:recipes} lists the image operations and parameters for
each recipe.

\subsection{A fixed workload and two measurement windows}

We select the first 10,000 \texttt{val/*.JPEG} members after lexicographic sorting
of a SHA-256-verified ImageNet validation archive~\cite{imagenet}. Before any
cells are timed, the VM reads every selected file once. This reduces cold-cache
order effects. Timed accesses use filesystem calls and normally retrieve
compressed bytes from the Linux page cache; decoding remains in the path.
These measurements do not estimate physical-disk bandwidth.

For each seed, the runner takes the first 8,448 files from a PCG64 permutation
of the 10,000 selected files. Every path receives that same ordered list.
A \emph{cell} measures one implementation, recipe, and seed. It consumes one
warm-up batch and then 32 timed batches, totaling 8,192 timed images. The timer
starts after synchronizing the warm-up batch and stops after synchronizing
the last measured batch. Throughput divides the measured image count by the
elapsed wall-clock time (Figure~\ref{fig:boundary}).

Pipeline construction and loader startup precede the timer. Prefetch can
prepare part of the measured workload before the timer starts, so the result
describes throughput over this fixed consumption window.

The NVIDIA Management Library (NVML) polls GPU memory for the implementation process at a nominal
\MemoryPollMs{}\,ms interval. It samples a baseline before building the cell's
pipeline and samples again after closing it. The peak is the largest reading
from that window, including the baseline. Each implementation reuses its
process across recipes and seeds. CUDA state and library allocations retained
from preflight or earlier cells can contribute to later baselines. Short peaks
can fall between samples.

\subsection{Eight input paths}
\label{sec:paths}

Table~\ref{tab:paths} shows where each path decodes, augments, and normalizes
a batch~\cite{pillow,torchvision,kornia,albumentationsx,dali}. Both Pillow paths use
the same adapter with a different \texttt{PIL} package in each process.
Pillow-AllSIMD can trade arithmetic precision for speed in fast mode~\cite{allsimd}.
The worker recorded AVX2 and fast mode. Both Pillow paths transfer pinned
\texttt{uint8} batches to CUDA and normalize there. AX uses its batch
\texttt{InputNormalizer} with FP32 arithmetic and FP16 output. Its preflight
verified the fused Triton kernel on a full batch outside the timed cells.

The TorchVision and Kornia GPU paths run the prefix through the first
shape-forming resize, crop, or letterbox on the CPU so the images can be stacked.
For a recipe that ends there, only normalization and output preparation run
on the GPU.

The TorchVision adapter typically calls GPU transforms per image and stacks
the results. Its JPEG recipe uses batched CUDA encode and decode, with JPEG
bytes passed through host memory between the calls. Kornia calls its GPU
module on the batch, with \texttt{same\_on\_batch=False} where supported.

\subsection{Recipe mappings and exclusions}
\label{sec:matching}

The catalog defines \RecipeCount{} recipes for individual RGB images.
An adapter maps each recipe to native operations. The added comparisons use
the same requested effect, parameters or sampling ranges, and output shape.
Some earlier recipes retain differing mappings, such as the Affine recipe
(R08). Appendix~\ref{app:semantics} describes these differences.

The report includes \ProductionPairCount{} implementation--recipe pairs with
three seeds each.

The cell seed controls the file order, the DALI graph seed, and the main
process's Python, NumPy, and PyTorch RNGs. DataLoader worker initialization
uses a loader generator seeded with zero, and AX Compose has its own RNG
without an explicit seed. The three observations therefore repeat the
workload with specified file orders and library-specific augmentation draws.
The timed consumer checks CUDA device, FP16 type, rank and channel axis. The
report also checks the recorded final batch shape against the manifest.

\section{Limitations}

The measurements apply to the adapters, worker settings, GPU, batch size,
and file inventory reported here.
The recipe mappings can change both the pixels and the amount of work.
The end-to-end timing cannot attribute a difference to one decoder or
transform. A training benchmark would also need to measure competition for
GPU compute and memory with the model running.

\paragraph{Author relationship.}
The author maintains \ax{}. Source, mappings, per-seed observations, and
result-generation code are provided so readers can inspect the choices behind
the comparison.

\section{Implementation semantics that affect interpretation}
\label{app:semantics}

\paragraph{Crop and resize.}
R01 and R03 request bilinear resampling without antialiasing. AX uses
\texttt{INTER\_LINEAR}. TorchVision and DALI explicitly disable antialiasing
in those rows. The Pillow paths use bilinear affine resampling, and Kornia
uses bilinear resize with \texttt{align\_corners=False}. In R03, crop sampling,
fallbacks, and rounding can differ. The Pillow adapter tries up to ten
candidate crops and then resizes the whole image if none fits.

RandomCrop224 takes a window at decoded resolution and pads with zeros when
needed. DALI uses an integer-offset slice and centers the padding on short
axes. The benchmark verified on L4 that the crop preserves source pixels and
pads undersized inputs. R50 and R51 explicitly resize by side before
cropping~\cite{daliresize}.

\paragraph{VerticalFlip (R05).}
The DALI adapter sets \texttt{horizontal=0} and \texttt{vertical=1}
for vertical-only reflection~\cite{daliflip}.

\paragraph{Shear (R46).}
In pixel-center coordinates, each path maps \(x\) to
\(x+\tan(10^\circ)(y-111.5)\) and leaves \(y\) unchanged. Sampling is bilinear,
with zero-valued neighbors outside the frame. The median throughput was
\AXShearSpeed{} images/s for AX. The appendix reports throughput and peak
process memory for all eight paths.

\paragraph{Affine (R08).}
AX samples rotation in \([-25^\circ,25^\circ]\) with fixed per-axis
translation and shear. TorchVision also samples rotation but interprets the
shear pair as a range for X shear and draws translation using the configured
fractions of the image size. The Pillow paths use a fixed matrix and the
first shear value. Kornia uses a fixed angle and drops the list-valued shear
parameter. DALI uses only scale and shift.

\paragraph{Brightness and blur.}
In R30, AX 2.6.2, DALI, and the Pillow paths use a fixed brightness factor
of 1.2. TorchVision samples a factor in \([0.8,1.2]\). Kornia adds 0.2 in
unit-range intensity coordinates. In GaussianBlur (R15), Pillow's filter
approximates a Gaussian with box filters~\cite{pillowfilters}. R32 applies a
\(5\times5\) box in every measured path. AX, Kornia, and DALI reflect the
boundary, and the Pillow paths extend the edge pixels.

\paragraph{Additional single-image recipes.}
The expanded catalog includes center and fixed crops, crop-and-pad,
letterboxing, padding, scale and rotation, channel operations, colorization,
dithering, box erasing, morphology, embossing, and pixel displacement.
The adapters use native functions or compositions such as a byte lookup or
channel splitting and merging. ModeFilter is outside the selection.
Mosaic, reference-image histogram matching, and box-aware crops require
different inputs. The DALI grid mask drops squares, while AX GridMask
drops stripes.

\paragraph{Dithering (R65).}
All three paths apply binary Floyd--Steinberg error diffusion to grayscale
pixels. AX accumulates error in floating point and quantizes at half scale.
The Pillow paths accumulate integer error terms and use white when the
corrected byte value exceeds 128. These arithmetic choices can produce
different output pixels.

\paragraph{Elastic (R10).}
The AX spline-grid settings were calibrated against the TorchVision and
Kornia displacement fields on CPU, targeting about 0.74 px RMS displacement
and a 10 px autocorrelation scale. The benchmark retains those catalog
settings. Matching these two statistics leaves differences in the fields
and their boundary effects. The calibration procedure is in
\texttt{docs/rgb\_elastic\_calibration.md}.
