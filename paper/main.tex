\begin{abstract}
We measure how many ready batches per second eight image input pipelines
deliver to an NVIDIA L4. Each pipeline starts with RGB JPEG files and delivers
synchronized CUDA float16 batches of 256 images. The benchmark contains
\ProductionCellCount{} measurements across \RecipeCount{} recipes. On the
\CommonRecipeCount{} recipes shared by all eight paths, DALI delivered a
median of \CommonBatchRateDALIGPU{} batches/s and AlbumentationsX (AX) delivered
\CommonBatchRateAlbumentationsX{}. DALI was fastest on \CommonDALIFastest{} of
those recipes. Median peak process GPU memory was \CommonMemoryDALIGPU{} MiB
for DALI and \CommonMemoryAlbumentationsX{} MiB for AX.
\end{abstract}

\section{Keep the next batch ready}

The loader can prepare the next batch while the GPU trains on the current
one. If the GPU finishes its step before the next batch is ready, it waits
(Figure~\ref{fig:batch-wait}) \cite{datastalls}.

\begin{figure}[H]
\centering
\input{batch-wait.tex}
\caption{Waiting for input reduces training steps per unit time. Both
schedules start with batch 1 ready and use the same GPU step duration.
Below, step 1 ends before batch 2 arrives, so the GPU sits idle until
the loader supplies it. The timings are illustrative.}
\label{fig:batch-wait}
\end{figure}

Input stalls can come from storage, decoding, augmentation, batching, or
transfer \cite{datastalls}. This benchmark measures those stages together,
up to a batch ready for the model. Operator benchmarks time selected routines
\cite{pytorchbenchmark}; training benchmarks such as MLPerf also include
the model and measure progress toward a quality target \cite{mlperf}.

\section{Benchmark design}
\label{sec:workload}

\subsection{Input and timing}

Each measurement covers one implementation, one recipe, and one seed.
After one warm-up batch, the runner times delivery of 32 batches through
the final CUDA synchronization. Batch rate is 32 divided by elapsed
wall-clock seconds. The runner reads the selected ImageNet JPEGs
\cite{imagenet} before timing to reduce the influence of storage. Every
path uses the same file order for a given seed. Decoding remains part of
batch preparation.

\subsection{Which recipes can be compared?}

A recipe specifies the image operations, for example crop followed by
equalization. We align the intended effect, output shape, and parameters
where the APIs permit. Matching a recipe does not guarantee identical
pixels or identical work. Crop offsets, padding, interpolation, and
arithmetic can differ. Appendix~\ref{app:recipes} gives the parameters
and Appendix~\ref{app:semantics} documents the differences.

The report combines three immutable runs with the same dataset, recipes,
hardware settings, and package locks. Each cell retains its source run and
cell ID. Appendix~\ref{app:reproduce} lists the manifests.

AX was faster than either Pillow path on most shared recipes. Pillow and

\subsection{AX vs TorchVision}

AX beat both TorchVision paths on most shared recipes. The
\PlotTorchVisionShared{} common recipes include geometry, color
operations, GaussianBlur, Equalize, and JPEG compression. MedianBlur and

On GaussianNoise (R16), TorchVision went from 4.8 batches/s on CPU to

\section{Use the results in a training job}

Start with how often the model needs a batch. For example, a 55\,ms
model step needs about 18.2 batches/s at the same batch size. On the
crop-only recipe (R02), DALI delivered \CropDALIBatchRate{} batches/s and
AX delivered \CropAXBatchRate{}. That makes DALI a candidate to test for
this example. The benchmark measures each loader in isolation. With the
model running, GPU preprocessing can compete for compute and memory, so
measure training throughput again with the candidate pipeline.

If the model still waits for input, locate the slow stage. For storage,
try faster media, larger reads from shards, indexed region reads for
large images or volumes, or caching compressed files. Changing codecs
changes both read volume and decode work. When the input queue empties
and CPU and I/O have spare capacity, try more workers. Deeper prefetch
can absorb short stalls at the cost of larger buffers \cite{pytorchdata}.
If batch preparation still limits delivery, compare decoders and
augmentation paths on the job's actual recipes.

If GPU memory is tight, a smaller device batch can reduce per-step
memory. Gradient accumulation can preserve examples per optimizer update
\cite{pytorchamp}. Batch normalization still uses the samples in each
forward pass. Retune workers and prefetch at the new batch size.
DataLoader prefetch generally uses host memory, and native GPU pipelines
can also buffer on the device. Compare training examples per second
after changing batch size.

\section{Timing, sampling, and output details}
\label{app:setup}

The runner selects the first 10,000 validation JPEGs in lexicographic order
and reads them once before timing. Each seed selects the first 8,448 files
from a PCG64 permutation of that list. After synchronizing the warm-up
batch, the runner times the remaining 8,192 images. Pipeline and worker
setup precede timing. Prefetch can prepare part of the workload before the
timer starts. The selected JPEGs fit in the VM's 64 GB of host memory, so
sequential prewarming lets timed random file reads usually hit the Linux page
cache. File lookup, cache access, decoding, and augmentation remain in the
timer. The measurement does not establish cold-cache disk performance.

NVML samples process GPU memory at a nominal \MemoryPollMs{}\,ms interval
and takes readings before pipeline construction and after teardown.
Short peaks can fall between samples. The DataLoader generator and DALI graph
use the cell seed. The cell seed also initializes Python, NumPy, and PyTorch
RNGs in the worker processes. AX Compose uses base seed zero, combined with
its DataLoader worker seed. Augmentation draws are independent per image.

Normalization uses RGB means \((0.485,0.456,0.406)\) and standard deviations
\((0.229,0.224,0.225)\) on the unit intensity scale. The runner validates
CUDA placement, FP16 type, and BCHW output. The catalog's \texttt{ToTensor}
stage describes this output contract.

TorchVision GPU reads JPEG bytes in DataLoader workers, decodes each batch with
NVJPEG, applies crop and other shape-forming transforms to each decoded image,
then stacks the results. Kornia GPU uses its Rust JPEG reader and runs the
shape-forming prefix on CPU because source images can have different sizes.

TorchVision GPU transforms draw random parameters per image. JPEG compression
draws a quality from 30 through 90 independently for each image, groups equal
qualities for encoding, then restores input order after CUDA decoding. Kornia
RGB augmentation draws per-image parameters, including its ColorJitter order.

\subsection{Implementation differences}
\label{app:semantics}

\paragraph{Crop and resize.}
R01 and R03 request bilinear resampling without antialiasing. AX uses
\texttt{INTER\_LINEAR}. TorchVision and DALI explicitly disable antialiasing
in those rows. The Pillow paths use bilinear affine resampling, and Kornia
uses bilinear resize with \texttt{align\_corners=False}. In R03, crop sampling,
fallbacks, and rounding can differ. The Pillow adapter tries up to ten
candidate crops and then resizes the whole image if none fits.

RandomCrop224 takes a window at decoded resolution and pads with zeros when
needed. DALI decodes the requested source window when the JPEG crop is valid.
It then pads short axes with zeros at the centre. RandomResizedCrop uses the
decoder's per-image crop followed by resize. R50 and R51 resize by long or
short side before cropping~\cite{daliresize}.

\paragraph{VerticalFlip (R05).}
The DALI adapter sets \texttt{horizontal=0} and \texttt{vertical=1}
for vertical-only reflection~\cite{daliflip}.

\paragraph{Shear (R46).}
In pixel-center coordinates, each path maps \(x\) to
\(x+\tan(10^\circ)(y-111.5)\) and leaves \(y\) unchanged. Sampling is bilinear,
with zero-valued neighbors outside the frame.

\paragraph{Affine (R08).}
Every R08 path applies the same fixed centered warp: scale 2, rotation 25°,
shear 10° on X and 15° on Y, and translation 20 pixels on both axes. Each
implementation performs all four operations in one affine transform.
Coordinate conventions, interpolation arithmetic, and rounding can still
produce small pixel differences.

\paragraph{Brightness and blur.}
R30 uses a fixed brightness multiplier of 1.2. R31 uses contrast factor 1.2
around each image's grayscale mean. R11 samples ColorJitter factors and
operation order independently for each image. DALI uses its native RGB-space
hue approximation. R24 draws an integer JPEG quality from 30 through 90 per
image. Kornia and DALI simulate JPEG artifacts, while TorchVision, AX, and
Pillow encode and decode JPEGs, so a shared nominal quality does not imply
pixel-identical output. In GaussianBlur (R15), Pillow's filter approximates a
Gaussian with box filters~\cite{pillowfilters}. R32 applies a
\(5\times5\) box in every measured path. AX, Kornia, and DALI reflect the
boundary, and the Pillow paths extend the edge pixels.

\paragraph{Omitted recipes and grid masks.}
Mosaic, reference-image histogram matching, and box-aware crops require
different inputs. The DALI grid mask drops squares, while AX GridMask
drops stripes.

\paragraph{Dithering (R65).}
All three paths apply binary Floyd--Steinberg error diffusion to grayscale
pixels. AX accumulates error in floating point and quantizes at half scale.
The Pillow paths accumulate integer error terms and use white when the
corrected byte value exceeds 128. These arithmetic choices can produce
different output pixels.

\paragraph{Elastic (R10).}
The AX spline-grid settings were calibrated against the TorchVision and
Kornia displacement fields on CPU, targeting about 0.74 px RMS displacement
and a 10 px autocorrelation scale. The benchmark retains those catalog
settings. Matching these two statistics leaves differences in the fields
and their boundary effects. The calibration procedure is in
\texttt{docs/rgb\_elastic\_calibration.md}.
