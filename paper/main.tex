\begin{abstract}
A training step can run only as fast as the input pipeline delivers batches. We measure eight
RGB input paths on one NVIDIA L4, from ImageNet JPEG files on local disk to a normalized
\texttt{float16} CUDA batch: AlbumentationsX, Pillow, Pillow-AllSIMD, TorchVision and Kornia on
the CPU and on the GPU, and NVIDIA DALI. Each of the \ProductionCellCount{} input-pipeline measurements records
images per second and peak process GPU memory in the same pass, over \RecipeCount{} augmentation
recipes and \SeedCount{} seeds. On the \CommonRecipeCount{} recipes all paths support, DALI
delivers a median of \CommonSpeedDALIGPU{} images/s and holds \CommonMemoryDALIGPU{} MiB of GPU
memory; the CPU paths deliver \CommonSpeedKorniaCPU{} to \CommonSpeedAlbumentationsX{} images/s
and hold \CommonMemoryAlbumentationsX{} to \CommonMemoryKorniaCPU{} MiB. When the same batches
feed a compiled \texttt{bfloat16} ResNet training step, most of these differences disappear. With
ResNet-50, every path that hands the training loop a finished batch keeps the step at
\TrainReadyFloorResNetFifty\% or more of its input-free rate, while the two paths that augment on
the GPU inside the training loop fall to \TrainMinResNetFiftyKorniaGPU\% and \TrainMinResNetFiftyTorchVisionGPU\%
on the heavier recipes. With the faster ResNet-18, the slower CPU paths also start to hold the
model back. The author maintains AlbumentationsX; the code, run manifests, and per-seed results
are public.
\end{abstract}

\section{The question}

The data loader prepares the next batch while the GPU trains on the current one. If the GPU
finishes first, it waits (Figure~\ref{fig:batch-wait}) \cite{datastalls}. How long it waits
depends on the JPEG decoder, the augmentations, where they run, and how many CPU cores prepare
batches. Operator benchmarks time single routines \cite{pytorchbenchmark}, and training
benchmarks such as MLPerf time a whole model to a quality target \cite{mlperf}. Neither tells a
practitioner which input path keeps a given model busy.

\begin{figure}[H]
\centering
\input{batch-wait.tex}
\caption{The GPU completes fewer training steps when batches arrive late. Both schedules use
the same step duration; the timings are illustrative.}
\label{fig:batch-wait}
\end{figure}

This report measures eight input paths at one fixed operating point in two ways:

\begin{enumerate}
\item \textbf{Input pipeline alone.} How many images per second each path turns into a
normalized CUDA batch, and how much GPU memory the process holds while doing it
(Section~\ref{sec:loader}).
\item \textbf{Feeding a training step.} How fast a compiled ResNet-18 or ResNet-50 trains when
each path feeds it, as a share of the same step on data already in GPU memory
(Section~\ref{sec:training}).
\end{enumerate}

\paragraph{Author disclosure.} The author maintains AlbumentationsX (AX), and AX transforms define
the reference effect of each recipe. Three things limit the effect of that position on the
results. Every setting is frozen in a public execution contract before a run. Every cell keeps
its run and cell identity, so any number in this report traces to a stored measurement. The
main tables and figures use images per second, a unit that does not depend on any one library;
comparisons with AX appear in their own section.

\section{Benchmark design}
\label{sec:design}

\subsection{What one measurement covers}

A measurement, or \emph{cell}, is one path, one recipe, and one seed. After one warm-up batch the
runner times the delivery of 32 batches of \BatchSize{} images up to the final CUDA
synchronization. Inside the timer are file lookup, decoding, the recipe, batching, the host to
device copy, any GPU work, normalization, and output validation. Outside it are imports,
pipeline construction, and a one-batch preflight. Every path returns the same output: a CUDA
\texttt{float16} tensor of shape \(\BatchSize\times3\times224\times224\), normalized with the
ImageNet mean and standard deviation on the GPU.

NVML samples the process's GPU memory every \MemoryPollMs{}\,ms from before pipeline
construction to the end of the cell. The reported peak therefore includes the CUDA context and
anything the process retained from earlier cells. Throughput and memory come from the same pass.

\subsection{Recipes}

A recipe is a short sequence of image operations, such as a random \(224\times224\) crop followed
by histogram equalization. Most of the \RecipeCount{} recipes add one augmentation to the crop or resize that forms the
\(224\times224\) shape, so a result isolates that augmentation's cost. A recipe runs on every path that can express
it with its own public operators: AX transforms define the target effect, TorchVision and Kornia
use their native operators with parameters set toward that effect, and the Pillow and DALI paths
compose native primitives. A path that would need a custom implementation of the effect is left
out of that recipe, and an unsupported recipe never counts against a path. Matching a recipe does
not make the pixels identical: crop rounding, interpolation arithmetic, and samplers differ.
Appendix~\ref{app:recipes} lists every recipe and Appendix~\ref{app:semantics} the differences
that remain.

\subsection{Reading the numbers}
\label{sec:statistics}

A cell's throughput is its median over the \SeedCount{} seeds. Because the seeds of a path ran as
separate jobs, usually on different VMs, the spread between seeds includes differences between
machines: across all
path--recipe pairs, the range between the slowest and fastest seed has a median of
\SeedSpreadMedian\% of the median, and one pair in ten exceeds \SeedSpreadNinety\%.

Two kinds of interval make that spread explicit. For one cell, the range from the slowest to the
fastest of five seeds covers the median with probability \(1-2\cdot2^{-5}=93.75\%\). For a ratio
between two paths on one recipe, we use the Hodges--Lehmann interval \cite{hodgeslehmann}: order
the \(5\times5\) pairwise ratios and keep those inside the exact Mann--Whitney bounds
\cite{mannwhitney}, which gives \(96.8\%\) coverage. A path is \emph{faster} or \emph{slower} on a
recipe only when this interval excludes 1; otherwise the two are \emph{tied}. These intervals
assume only that the seeds are exchangeable. A statistically clear difference can still be
small, so the figures show the size of every ratio as well.

\section{Input pipeline alone}
\label{sec:loader}

Figure~\ref{fig:overview} shows every path on the \CommonRecipeCount{} recipes that all eight
support. DALI delivers the most images per second: a median of \CommonSpeedDALIGPU{}, and the
highest median on \CommonDALIFastest{} of the \CommonRecipeCount{} recipes. Its graph decodes on
the GPU and holds \CommonMemoryDALIGPU{} MiB of GPU memory. Among the
paths that augment on the CPU, AX has the highest median (\CommonSpeedAlbumentationsX{}),
followed by Pillow-AllSIMD (\CommonSpeedAllSIMD{}), TorchVision CPU (\CommonSpeedTorchVisionCPU{}),
and Pillow (\CommonSpeedPillowCPU{}); these paths hold \CommonMemoryAlbumentationsX{} to
\CommonMemoryKorniaCPU{} MiB. The Kornia paths deliver the fewest images per second on this set
(\CommonSpeedKorniaGPU{} on the GPU, \CommonSpeedKorniaCPU{} on the CPU).

\section{Feeding a training step}
\label{sec:training}

A loader that delivers more images per second than the model consumes cannot speed up training.
To see which differences survive, each delivered batch feeds one training step of an untrained
torchvision ResNet-18 or ResNet-50 \cite{resnet} on the same L4: \texttt{torch.compile}
\cite{pytorch2}, \texttt{bfloat16} autocast, \texttt{channels\_last}, and SGD with fixed random
labels. The step does not measure accuracy.

\paragraph{The ceiling.} Before the loader starts, the same process runs the step on one batch
already in GPU memory; this also compiles the model. That rate is the step's \emph{ceiling}:
\TrainCeilingResNetEighteen{} images/s for ResNet-18 at batch \TrainBatchResNetEighteen{} and
\TrainCeilingResNetFifty{} images/s for ResNet-50 at batch \TrainBatchResNetFifty{}. Each cell
reports its training throughput as a share of its own ceiling, so differences between machines
cancel.

\paragraph{The workload.} The training runs use all 50,000 validation JPEGs, enough for 10 warm-up
and \TrainMeasuredBatches{} measured batches without reading a file twice. Recipes form a ladder of
common ImageNet training augmentations: random resized crop and horizontal flip; then
ColorJitter; then ColorJitter and random erasing; and, separately, RandAugment
\cite{randaugment} with two operations at magnitude 9. TorchVision, Kornia, and DALI run their
native RandAugment; AX and Pillow assemble the same 14 operations from stock transforms and
primitives. Pillow has no ColorJitter or erasing in this catalog, so those two recipes run on six
paths.

\begin{figure}[H]
\centering
\input{generated/fig-training.tex}
\caption{Training-step throughput as a share of the model-only ceiling, per path and recipe; the
whiskers are the seed interval. A path at 100\% keeps the model fully fed.}
\label{fig:training}
\end{figure}

Figure~\ref{fig:training} shows two regimes. ResNet-50 at batch 128 consumes about
\TrainCeilingResNetFifty{} images/s, and every path that hands the training loop a finished batch
keeps up: the step runs at \TrainReadyFloorResNetFifty\% or more of the ceiling on every recipe. ResNet-18 consumes about \TrainCeilingResNetEighteen{} images/s,
and there the slower CPU paths show: once ColorJitter is in the recipe, TorchVision CPU falls to
\TrainMinResNetEighteenTorchVisionCPU\% and Kornia CPU to \TrainMinResNetEighteenKorniaCPU\%, while AX stays between
\TrainMinResNetEighteenAlbumentationsX\% and \TrainMaxResNetEighteenAlbumentationsX\% and
Pillow-AllSIMD between \TrainMinResNetEighteenAllSIMD\% and \TrainMaxResNetEighteenAllSIMD\%.

Kornia GPU and TorchVision GPU behave differently. They apply the recipe on the GPU inside the
training loop, after it receives the batch, so that work takes GPU time from the step itself. With ResNet-50 they reach \TrainMinResNetFiftyKorniaGPU\% and
\TrainMinResNetFiftyTorchVisionGPU\% of the ceiling on the heavier recipes; with ResNet-18,
\TrainMinResNetEighteenKorniaGPU\% and \TrainMinResNetEighteenTorchVisionGPU\%. DALI also augments on
the GPU, but inside its own pipeline before it hands over the batch, and stays between
\TrainMinResNetEighteenDALIGPU\% and \TrainMaxResNetEighteenDALIGPU\% with ResNet-18 and
between \TrainMinResNetFiftyDALIGPU\% and \TrainMaxResNetFiftyDALIGPU\% with ResNet-50, and holds 1--2 GiB
more GPU memory than the CPU paths. Appendix~\ref{app:training} lists every training cell.

\section{Where the results apply}

The results describe one operating point: one L4, 16 vCPUs, 15 workers, batch 256 for the input
pipeline, and files already in the page cache. More or fewer CPU cores, another GPU, cold storage,
or larger images could change the ranking. The input-pipeline numbers bound what a loader can
deliver; the training numbers show what reaches two particular models. By the same logic, a model
slower than ResNet-50 should hide the loader even more, and a faster one, or a faster GPU, expose
it more. The recipes request the same effects, but the paths do not produce identical pixels, and
the benchmark does not measure the quality of the augmented images or the accuracy of a trained
model. Tied results mean the seeds cannot separate the paths at this sample size; they do not
prove the paths equal.

To use the results for a training job, start from the model: measure its step rate on data in GPU
memory, then compare it with the delivery rates in Section~\ref{sec:loader} for the job's recipe.
If a path delivers well above that rate, the loader is not the bottleneck.

Version 3 measures \SeedCount{} seeds instead of 3, runs AX 2.6.9 with \texttt{ToTensorV2} before

\section{Timing, sampling, and output details}
\label{app:setup}

The runner selects the first 10,000 validation JPEGs in lexicographic order, removes their EXIF
headers so every decoder reads the stored pixel orientation, and reads them once before timing.
Each seed takes the first \(\BatchSize\times33\) files of a PCG64 permutation; the first batch
warms up and the remaining 32 are timed. The files fit in the VM's 64 GB of memory, so the timed
reads usually hit the Linux page cache; the measurement does not cover cold storage.

Every stochastic stage draws its parameters for each image. The DataLoader generator, the DALI
graph, and the worker processes are seeded with the cell seed. Each implementation runs in its
own process through all of its recipes. Before timing, every path--recipe pair passes a
one-batch preflight that checks the output's device, type, and shape.

For the training step, the runner compiles the model once per process and restores its initial
weights before each cell, so later cells reuse the compiled graph. The training data are all
50,000 validation JPEGs; one file is a CMYK JPEG that some decoders reject, and the preparation
step re-encodes it as RGB at quality 95 so that every path reads the same image.

\section{Implementation differences}
\label{app:semantics}

\paragraph{Resize and crops.} Resize (R01) and RandomResizedCrop (R03) use bilinear interpolation
without antialiasing. AX uses OpenCV's \texttt{INTER\_LINEAR}; TorchVision and DALI disable
antialiasing explicitly; the Pillow paths use an affine transform because Pillow's resize
smooths when it downsamples; Kornia uses \texttt{align\_corners=False}. RandomCrop224 samples a
window at the decoded resolution and pads short sides with zeros in the center. DALI decodes only
the requested window when a recipe starts with a compatible crop.

\paragraph{Geometry.} Rotate (R07) draws an angle in \([-45^\circ, 45^\circ]\) and warps once
with bilinear sampling and zero fill. Affine (R08) draws a scale in \([0.75, 1.25]\), a rotation
within \(\pm15^\circ\), two shears within \(\pm8^\circ\), and two shifts within \(\pm12\) pixels;
TorchVision and Kornia use their native \texttt{RandomAffine} with shifts expressed as fractions
of the crop. Perspective (R09) follows AX's corner sampling; TorchVision rounds the sampled
corners, and Kornia keeps its own uniform corner sampler. Shear (R46) draws an X shear within
\(\pm10^\circ\) for each image.

\paragraph{Elastic (R10).} AX, TorchVision, and Kornia draw a new displacement field and an
amplitude between 0.5 and 1 for each image. The settings were calibrated to about 0.74 pixels of
RMS displacement and a 10-pixel spatial scale; the fields still differ between libraries. DALI and
Pillow have no Elastic recipe.

\paragraph{Color and filters.} ColorJitter samples factors and operation order for each image;
DALI's hue adjustment approximates the HSV rotation in RGB space. CLAHE (R29) uses an
\(8\times8\) grid: AX equalizes Lab lightness, Kornia each RGB channel, and DALI luma. JPEG
compression (R24) draws a quality from 30 to 90 for each image; Kornia and DALI simulate the
artifacts, while the other paths encode and decode. Pillow's GaussianBlur approximates a Gaussian
with box filters \cite{pillowfilters}. Dithering (R65) accumulates error in floating point in AX
and in integers in Pillow, so their pixels can differ. ModeFilter, Mosaic, reference-image
histogram matching, and box-aware crops are outside this workload.

\paragraph{RandAugment.} Every path applies two operations per image at magnitude 9 of 31 bins,
with bilinear warps and zero fill. TorchVision, DALI, AX, and Pillow use the same 14 operations
and draw them with replacement; AX and Pillow take their magnitudes from TorchVision, and a test
checks each operation against TorchVision's pixels. Kornia draws without replacement from its own
pool and picks one sequence per call, so its adapter calls it once per image. DALI translates by
up to 100/224 of the side instead of 150/331, and AX implements Sharpness with an unsharp mask.
