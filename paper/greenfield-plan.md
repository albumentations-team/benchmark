# Greenfield-план статьи о RGB JPEG-to-GPU benchmark

Дата: 6 сентября 2026 года.

## 1. Что должна дать новая статья

Написать заново английскую эмпирическую статью для ML-инженера, который выбирает
путь подготовки изображений для модели. После чтения он должен понимать:

1. Какую задачу решает сравнение и какие условия зафиксированы.
2. Что выполняет каждый измеренный путь, включая CPU, GPU и декодирование.
3. Как различаются throughput и потребление GPU memory на нужных ему recipes.
4. Насколько выбранный каталог преобразований покрывается каждой библиотекой.
5. Какие выводы можно перенести в свой проект и что нужно проверить отдельно.

Основной эмпирический вывод: на зафиксированной RGB-нагрузке DALI быстрее AX
на их измеренном пересечении, а AX быстрее выбранных Pillow, TorchVision и
Kornia paths на большинстве общих recipes. Статья должна показать величину
различий, исключения и сопутствующее потребление памяти. Каталог поддерживаемых
преобразований задаёт отдельное условие выбора библиотеки.

Текущая структура `main.tex`, формулировки и графики не задают архитектуру новой
статьи. Источники истины — измерения, код измеренного запуска, конфигурация и
каталоги. Текущий текст используется только как перечень утверждений, которые
нужно заново проверить.

Результат выполнения плана: новая статья, собранный PDF, сгенерированные из
данных таблицы и графики, одна таблица результатов для самостоятельного анализа.
Сам этот план не запускает переписывание статьи или новые измерения.

## 3. Новая последовательность изложения

### 3.1. Какой выбор помогает сделать эксперимент

Открыть статью конкретной задачей: приложению нужен следующий готовый batch,
а разные библиотеки распределяют подготовку между декодером, CPU и GPU.
Сформулировать вопрос о числе готовых изображений в секунду и памяти процесса.

Коротко установить границу применения: модель в эксперименте отсутствует.
Сокращение времени обучения этим запуском не измерено. Для GPU-аугментаций
совместное использование GPU с моделью также требует отдельной проверки.

Затем объяснить выбор JPEG-to-GPU boundary: он включает работу, которую
приложение обязано выполнить, чтобы передать изображения модели. Разные
декодеры и размещение операций остаются частью сравниваемых путей.

### 3.2. Что получает и возвращает один тест

До перечня библиотек определить recipe на двух конкретных примерах:

```text
RandomCrop224 → Normalize → ToTensor
RandomCrop224 → Equalize → Normalize → ToTensor
```

Показать общий вход — JPEG с исходными размерами из выбранного списка файлов — и
общий выход: RGB, CUDA float16, BCHW, 256 × 3 × 224 × 224. Объяснить каждый
размер один раз. Для второго примера throughput относится ко всему пути с
Equalize; стоимость самого Equalize отдельно не измеряется.

Названия стадий recipe описывают требуемое преобразование данных. Физическое
место преобразования в tensor, смены layout и dtype показать в описании paths:
библиотеки не обязаны исполнять один и тот же буквальный вызов `ToTensor`.

### 3.6. Какие преобразования доступны и как применить выводы

После измерений дать короткий самостоятельный раздел coverage. Назвать единицу
подсчёта: запись выбранного RGB 2D каталога AX, для которой найдено соответствие
в другой библиотеке. Один API конкурента может соответствовать нескольким
записям; это не подсчёт уникальных API или всех возможностей конкурента.

Объяснить связь с 57 recipes: один класс может порождать несколько recipes,
а часть классов не измерялась. DALI участвует только в execution benchmark.
Отсутствие DALI в census не изображать нулём.

Закончить последовательностью действий для читателя: проверить нужные
преобразования, найти соответствующие измеренные recipes, сопоставить speed и
memory, затем проверить свой полный pipeline вместе с моделью. Произвольная
композиция нескольких измеренных преобразований не получает автоматически
доказанную скорость из отдельных строк.

## 4. Объяснение решений через условия эксперимента

| Решение | Что объяснить читателю | Какую границу вывода сохранить |
| --- | --- | --- |
| JPEG → готовый CUDA batch | Приложению нужен полный путь подготовки; reader, decode, collate, transfer и normalization входят в задачу | Разница throughput относится ко всему пути; вклад отдельного kernel не выделен |
| Native reader и decoder | Библиотеки имеют разные способы подготовки данных; они сохраняются внутри общей входной и выходной границы | Это сравнение конкретных интеграций, а не изолированных augmentation kernels |
| RGB и ImageNet JPEG | Задать конкретную нагрузку: 10 000 первых отсортированных файлов, три канала, исходные размеры | Не заявлять репрезентативность для всех RGB-данных, медицинских изображений или видео |
| Prewarm файлов | Один полный предварительный read уменьшает различие между первым cold-cache проходом и последующими | Измеряются файловые вызовы и decode при прогретом cache; bandwidth физического диска не определяется |
| Один порядок файлов на seed | Все implementations получают одну перестановку без повторов | Общий seed не делает случайные параметры разных библиотек идентичными |
| 224 × 224, float16, batch 256 | Это принятый выходной контракт и фиксированная рабочая точка | Не называть значения оптимальными без отдельного поиска; Resize должен явно означать выход 224 × 224 |
| 15 workers и prefetch 2 | Настройки фиксированы для DataLoader paths; раскрыть также число DALI threads и его native queue | Одинаковое числовое значение prefetch не означает одинаковый объём очередей разных архитектур |
| CPU prefix у GPU paths | Разные исходные размеры нужно привести к collatable shape в выбранной реализации | Это ограничение данного пути с DataLoader, а не невозможность других GPU-реализаций |
| Normalize на GPU | Единое размещение финальной нормализации принято контрактом | Это решение benchmark; оно не доказывает превосходство над CPU Normalize |
| Per-image случайность и вызовы | Для каждой реализации указать область sampling и способ исполнения | Если причина вызова по одному изображению не подтверждена, описать факт без заявления, что API вынуждает именно такой путь |
| Один warm-up и 32 batches | Throughput равен 8 192 изображениям, делённым на время окна; синхронизация выполняется до и после окна | Окно включает асинхронную подготовку и очередь; не рисовать последовательную обработку каждого batch или доказанное насыщение |

Не восстанавливать мотивацию автора по одному значению в конфигурации. Если
источник подтверждает только фиксированный выбор, назвать его условием
эксперимента. Отдельное обоснование «почему именно 256» требует существующего
свидетельства; такой выбор не следует выдавать за результат tuning.

Для отбора recipes описать воспроизводимое правило: реализованные полные пути
из зафиксированного каталога, поддерживаемые AX и хотя бы одним конкурентом.
Раскрыть ограничения отбора. Не утверждать, что каталог исчерпывает все
возможные сопоставимые recipes или является случайной выборкой преобразований.

## 5. Единые правила расчёта и интерпретации

### Throughput и выбор реализации

1. Для каждой пары implementation–recipe взять медиану throughput трёх seeds.
2. В общем пересечении сохранить семь implementations отдельными столбцами.
3. Для подсчёта побед по всем измеренным recipes TorchVision и Kornia выбрать
   path с большей медианой
   throughput данной recipe. При точном равенстве выбрать CPU path; это только
   детерминированное правило разрешения равенства. Сохранить выбранный path в данных.
4. GPU memory для такой recipe брать из того же выбранного path; не выбирать
   независимо минимальную память другой реализации.
5. Использовать одно направление относительной скорости во всей статье:
   `throughput выбранного path / throughput AX` на одной recipe.
   Значение `1×` означает одинаковую скорость, `2×` — вдвое больше изображений
   в секунду у сравниваемого path. Направление подписывать на каждом рисунке.
6. Для barplot на общем наборе из 11 recipes считать арифметическое
   среднее построчных ratios для каждой из семи implementations. На отдельных
   графиках показать средние для AX и каждого CPU/GPU path отдельно:
   три полоски для Kornia и TorchVision, две для Pillow и DALI. Набор recipes
   внутри графика общий для всех полосок: 46/25/26/22 соответственно.
   AX = 1×; каждая recipe имеет одинаковый вес.
7. Попарный median ratio считать по отношениям отдельных recipes. Не заменять
   его отношением общих медиан. При смене направления заново вычислять ratios
   из данных, а не обращать уже округлённый headline.

Количество побед — число строгих сравнений медиан. Точные равенства показывать
отдельно. Не вводить произвольный порог «ничьей» и не называть преимущество
статистически значимым по одному сравнению трёх seeds.

### GPU memory и разброс

Память — измеренный через NVML пик GPU memory процесса. Monitor работает в том
же pass, что throughput, но его окно начинается до построения pipeline.
Показатель включает память процесса и инфраструктуры; он не равен приросту
памяти отдельного преобразования. Это не CPU RAM и не только память tensor allocator.

Указать частоту опроса из raw records и ограничение дискретного sampling: очень
короткие пики между опросами могут не попасть в наблюдение. Не обещать точность
до байта или возможность вычислить максимальный trainable batch из этих данных.

По каждой recipe считать медиану memory трёх seeds. Для пар использовать
`memory выбранного path − memory AX`, затем медиану этих построчных разностей.
Не подменять её разностью общих медиан.

Развести два вида разброса:

- **Между seeds одной recipe:** сохранить все три значения и их min–max.
  Они характеризуют наблюдавшуюся повторяемость; это не доверительный интервал.
- **Между recipes:** медиана и 25–75-е процентили показывают неоднородность
  нагрузки. Использовать один метод квартилей — `inclusive`, как в генераторе.
  Такой интервал не показывает ошибку измерения или надёжность ранжирования.

Каждая recipe имеет одинаковый вес в summary. Это описательный итог по
выбранному набору, а не прогноз скорости типичного проекта с другим набором
преобразований и частотами их применения.

Одна схема показывает JPEG, обработку библиотекой и model-ready CUDA batch.
Под ней две временные полосы: throughput после warm-up и memory от construction
до финальной синхронизации. Явно обозначить работу prefetch и возможное

Всю раскладку семи paths поместить в отдельную таблицу: decoder, работа до
H2D, transfer dtype, работа после H2D, per-image/per-batch execution. Для DALI
описать native graph без искусственного помещения mixed decoder в CPU-колонку.

Сверять таблицу с frozen code. В частности, TorchVision GPU переводит batch в
float16 после H2D и вызывает оставшиеся transforms по отдельным изображениям.

### Рисунок: throughput на 11 общих recipes

Использовать heatmap: 11 строк recipes, шесть столбцов конкурирующих paths.
В каждой клетке напечатать отношение throughput к AX. Справа дать отдельный
столбец абсолютного throughput AX в images/s, чтобы относительные значения
имели видимый масштаб. Семь реализаций тем самым представлены без отдельного
столбца одинаковых значений `1×` для AX.

Цвет кодирует `log2(ratio)` с нейтральным цветом при `1×` и симметричными
границами вокруг нуля, покрывающими все значения. Подписанные числа остаются
обычными ratios. Никакого clipping значений и красно-зелёной шкалы.

Recipes расположить по структуре: базовые shape-forming recipes, затем
recipes с добавленным преобразованием. Общие стадии вынести в явное пояснение,
а короткие подписи связать с полными IDs в приложении. Столбцы CPU/GPU одной
библиотеки разместить рядом. Не сортировать строки по выгоде для AX.

Подпись объясняет: одна клетка — отношение медиан трёх seeds для одной recipe;
больше `1×` означает более быстрый competing path. Цвет показывает величину
разницы, а не статистическую значимость. Полные абсолютные значения доступны
в приложении и таблице данных.

### Рисунок: средние коэффициенты на общем наборе

Дополнить heatmap горизонтальным barplot: семь implementations на тех же
11 recipes, отсортированные по среднему коэффициенту. Использовать
арифметическое среднее построчных отношений throughput / AX throughput;
отношение отдельно усреднённых скоростей не подходит. Каждая recipe имеет
одинаковый вес. Медианы трёх seeds вычисляются до отношений.

Столбцы начинаются от нуля. Пунктир обозначает AX = 1×. Подписать коэффициент
на каждом столбце и направление «выше — быстрее». Дать полные CPU/GPU labels.
Рядом сохранить heatmap с отдельными recipes: среднее не заменяет её и не
является прогнозом для произвольного training pipeline.

### Рисунок: GPU memory на тех же 11 recipes

Семь горизонтальных полосок, по одной на implementation. Значение — медиана
построчных медиан peak process GPU memory в MiB. Начало оси — ноль, подпись
«Lower is better», числа на концах полосок. Сортировка от меньшей памяти к большей.
Сохранить индивидуальные результаты и разброс seeds в приложении и CSV.

### Четыре рисунка: AX vs Kornia, TorchVision, Pillow и DALI

Компактный barplot средних для каждой пары. AX/Kornia CPU/Kornia GPU — три
полоски на 46 общих recipes; AX/TorchVision CPU/TorchVision GPU — три на 25;
AX/Pillow CPU — две на 26; AX/DALI GPU — две на 22. Каждая полоса показывает
арифметическое среднее отношений throughput path / AX throughput по recipes.
Линия AX = 1×, линейная шкала от нуля, числа на концах полосок.

CPU/GPU path фиксирован для всей полоски. Набор recipes одинаков внутри каждого
графика и может различаться между графиками. Число recipes явно указать в подписи.
Подсчёт побед на всех измеренных recipes (51/26/26/22) оставить отдельным абзацем.
Построчные графики убрать; полные результаты сохранить в приложении и CSV.

### Таблица: coverage выбранного каталога

Четыре строки AX/Kornia/TorchVision/Pillow, количество сопоставленных записей,
версия census. В подписи прямо указать AX как исходный каталог. Четырёх чисел
достаточно для таблицы; отдельный bar chart не добавляет необходимого вывода.

Для полной проверки дать в приложении или сопровождающем каталоге соответствия
AX entry → API конкурента и ограничения сопоставления. DALI в этот подсчёт
не включать. Различие между coverage и execution объяснить на одном примере
класса, который порождает несколько recipes.

## 7. Границы выводов и научное позиционирование

По существующим результатам допустимы утверждения о наблюдаемой скорости и
памяти конкретных paths на обозначенных наборах recipes. Основные направления
сравнений проверить заново: преимущество DALI на его измеренном пересечении;
преимущество AX на большинстве общих recipes с остальными библиотеками;
исключения и величина различий.

Не выводить из этих данных:

- выигрыш во времени эпохи, accuracy или convergence;
- эффективность совместного использования GPU с моделью;
- причинный вклад декодера, transfer dtype, lookup tables или отдельного kernel;
- оптимальность batch/workers, универсальный порядок библиотек или результаты
  других каналов, разрешений, видео и volumes;
- эквивалентность пикселей, распределений случайных параметров или API;
- превосходство полного каталога AX над всеми возможностями других библиотек.

Related work должен объяснить место этого эксперимента среди kernel benchmarks,
измерений входных pipelines и измерений полного обучения. Использовать короткий
раздел с первичными источниками, которые действительно подтверждают различия.
Описания пяти библиотек сами по себе не заменяют позиционирование эксперимента.
Цитату AlbumentationsX брать из его собственной научной статьи; не подменять её
статьёй о legacy Albumentations. Библиографические данные проверить при переписывании.

Кратко указать связь автора с AX. Каталог зависимостей AX и история
его оптимизации не являются объяснением измеренного speedup без отдельных
измерений. Включать такие сведения только там, где они описывают фактический path.

## 8. Порядок выполнения и проверяемый результат

Всю работу выполняет автор переписывания последовательно в текущем repository.
Параллельные ветви статьи, второй генератор и новый benchmark framework не нужны.

| Шаг | Работа | Условие завершения |
| --- | --- | --- |
| 1. Собрать доказательства | Найти или получить raw cells данного run; проверить их существующим валидатором; прочитать frozen code/config и versioned census | 759 ожидаемых cells, полные пары метрик, известные версии; таблица paths соответствует измеренному коду |
| 2. Подготовить числа | Расширить существующий `generate_results.py` ровно под выбранные материалы | Общий набор 11, попарные наборы 51/26/26/22; правильные ratios, выбор paths, seed ranges и memory deltas |
| 3. Сделать материалы | Сгенерировать схему, heatmap, barplot средних, barplot памяти, четыре попарных barplot и три таблицы, описанные выше; полные результаты оформить приложением и одним `recipe-results.csv` | Любое число связано с raw cells или versioned census; CSV содержит 253 implementation–recipe строки и все три пары исходных seed-метрик |
| 4. Написать статью | Сначала методика и результаты, затем выводы и ограничения, после них начало и abstract | Каждый раздел отвечает на вопрос читателя; существенные условия известны до результатов |
| 5. Собрать и проверить PDF | Просмотреть все страницы при окончательной ширине; перечитать статью целиком и вслух | Числа и подписи читаются без увеличения, ссылки работают, наборы сравнения и смысл цветов и интервалов понятны |
| 6. Завершить замену | Удалить только ставшие ненужными тексты и генерируемые plot assets; обновить paper README и команду сборки | Одна статья, один путь генерации, воспроизводимая сборка; raw evidence и чужие изменения сохранены |

Сначала получить корректные данные для новых объектов, затем заменить текст
и убрать старые объекты одним переходом. Не вести две поддерживаемые версии
генератора или рукописи. Не удалять immutable evidence при очистке assets.

Если изменяется Python-генератор, выполнить обязательный `unslop-code` review
только его изменений и подходящие существующие проверки. Дополнительную
проверку добавлять лишь для новой существенной логики: например, выбор memory
того же path или направление median ratio. Для Markdown-плана кодовые тесты
не нужны.

Время работы ограничивается чтением, локальной агрегацией 759 records и сборкой
PDF. Новых платных вычислений нет. Если raw evidence не удаётся получить или
оно не проходит валидацию, остановить выпуск численных материалов и сообщить
конкретную проблему; не обходить её ручным переносом чисел из старого PDF.

## 9. Критерии готовности статьи

- После первой страницы читатель может назвать вопрос, вход, выход и область
  применения результатов.
- До первого результата определены recipe, implementation, cache state,
  batch, workers, hardware и оба окна измерения.
- Объяснение методики различает условия выбранного эксперимента, ограничения
  конкретной реализации и подтверждённые ограничения API.
- Каждый CPU/GPU path описан по frozen code, включая dtype при H2D и способ
  вызова преобразований. У GPU Normalize нет исключений.
- Различаются catalog entries, recipes, implementation–recipe pairs и seeds.
- Нельзя спутать общее пересечение с попарным, median ratio с ratio of medians,
  разброс между recipes с разбросом повторов или process peak с marginal memory.
- Throughput и GPU memory представлены вместе и получены из одного run.
- Все измеренные recipes доступны для проверки; отсутствие поддержки
  не превращено в нулевую скорость или поражение библиотеки.
- Абстракт, рисунки и подписи дают согласованную картину даже при отдельном чтении.
- Выводы про DALI, AX и исключения соответствуют данным; перенос на обучение
  сформулирован как вопрос для проверки, без обещанного ускорения эпохи.
- Нет ручных benchmark-чисел, непроверенных историй выбора параметров,
  необоснованных причинных объяснений и повторяющихся списков результатов.
